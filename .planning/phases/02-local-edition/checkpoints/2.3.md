## What changed

- `installation.py` (attested from now on): `from_environment()` (`HYPRN_MVP_CONFIG`), `owner()` = `hyprn-mvp-<edition>-<installation id>`, `profile_name()` = `hyprn-mvp-<edition>-<id8>`; the development store (no configuration) keeps `hyprn-mvp-execution` / `hyprn-mvp`.
- `launcher.py`: `HYPRN_MVP_DATA_ROOT` first (development), else the installation decides `ROOT` (`<data root>/execution`), `OWNER`, `PROFILE`, `DOCKER_ENDPOINT`; every docker call uses the configured endpoint (`docker_environment()`); `execution_configuration()` = data root, native profile, engine endpoint (a scope root is its own data root and profile), its digest is written by the worker builder into `runtime.json` (`execution_configuration_sha256`) and `identity()` refuses a mismatch ("Execution configuration changed … rebuild and re-attest"); the home-denial probe checks the account's home **and** the configured `host_home` (or a scope's `home`), never fewer than before. Worker policy unchanged and still source-only. `fixture_runtime_root` (scoped `hyprn-mvp-test-<uuid>` roots only) unchanged.
- `execution_runtime.py`: owner, endpoint and configuration digest from the launcher; worker sources copied into the build context with mode 0444.
- `calculation.PROFILE` and `native_environment` (profile in `initialize`/`evidence`) take the launcher's profile; `dispatch_runtime.py` roots already come from `local_paths` (step three, 2.2): docstring only.

## Remaining risks

- The `umask 077` of the entry point can make any other file written for a container (fixtures, modeling and application image contexts, a host-built UI) unreadable by a non-root container user; only the two cases above were met. Image builds should set explicit modes (relevant to 2.4, 2.6, 2.7).
- Containers and networks of the modeling and application managers do not yet carry installation-specific names or the configured endpoint (task 2.4).
