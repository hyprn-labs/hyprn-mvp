## What changed

- `installation.component_names(configuration)`: compose project, container and network names `hyprn-mvp-<edition>-<id8>-<role>` (modeling, private network, application, public network), every resource labelled `org.hyprn-mvp.owner=installation.owner(...)`; the development data root keeps its fixed names. `owner_username`, `docker_environment` and `NAME_PREFIXES` beside it. `local_paths.configured_installation()` (None while `HYPRN_MVP_DATA_ROOT` is set, as in the launcher), `component_names()`, `owner_username()`, `docker_environment()`, `installation_name_prefixes()`.
- `modeling_runtime`: root, upstream cache (resolver unchanged, fail-closed), engine endpoint on every docker and compose command, names and owner from the installation; the compose recipe reads container, network and owner from the clean compose environment (`${HYPRN_MVP_MODELING_*:?}`), the project name comes from `--project-name`. `stage_native_inputs` kept (it now also sets modes).
- `application_runtime`: root, port, names, owner, engine endpoint and the provisioned sign-in name (`owner_username`, argument to the bootstrap; the password stays on standard input) from the installation.
- Build-context modes (umask 077): `modeling_runtime.readable_context` gives folders 0755, files 0644 (start script 0755) and refuses links; applied to the modeling build context, to every `stage_native_inputs` stage and to the application build context. Evidence: a modeling image built from this tree under umask 077 (`modeling/rehearsal.py`) has 0 files below `/native` and the notice folder that the service user cannot read; the findings fixture's staged `modeling_contract.rb` is 0600 on the base tree and 0644 on this tree.
- Attestation (orchestrator scope): canary `worker_import` imports `hyprn_mvp_integration`, `.worker` and `.results` as the worker user and reports the SHA-256 of the bytes read; `passed` requires exit 0 and equality with the attested package, worker and results digests (`evidence.worker_import`). Placed here, not in 2.8: no conflict (2.8 re-attests anyway). A worker built with root-only package files (0400) passes every resource canary and is refused by this probe alone (new `units-attestation` case).
- `live_fence`: protects the path policy's per-OS default configuration and data root (account home), the configuration named by `HYPRN_MVP_CONFIG`, and the data root, upstream cache and port each configuration names (read leniently at import); refuses docker tokens naming `hyprn-mvp-<edition>-` resources or owners.
