# Build-backend audit for task 2.5 — draft for the product owner

Status: **draft, blocking**. Nothing has been installed and nothing has been changed in the product. Task 2.5 stops here until the product owner chooses a backend. Recorded on 2026-10-14 from official upstream sources only: PyPI JSON metadata, PyPI integrity API and the OSV batch API. Every SHA-256 below was read from PyPI metadata and then recomputed on a copy downloaded into a scratch folder outside the repository. The copies were inspected as zip archives only, and no code from them was run. This record covers provenance, licences and advisories. It is not legal advice.

## Why task 2.5 needs this

- The plan for task 2.5 says that `prepare` builds non-editable `hyprn-mvp-app` and `hyprn-mvp-integration` wheels from the snapshot with a pinned, hashed build backend, and installs them without dependencies.
- Decision D6 (b) (`docs/operations/dependency-audit.md` §10) says that the build backend is pinned exactly and audited at the first wheel build of the checkout's packages. Task 2.5 is that first build.
- Today the backend is not pinned anywhere:
  - `integration/pyproject.toml` declares `requires = ["setuptools>=61"]`, which is unpinned.
  - `application/pyproject.toml` has no `[build-system]` table. A PEP 517 frontend would therefore fall back to `setuptools.build_meta:__legacy__` with an unpinned setuptools.

## What else task 2.5 installs (already covered, no new review)

- **The native host lock is set N exactly.** It is the `native` group of `uv.lock` minus ruff, the style-ratchet tool, which the host environment does not need: 89 distributions. All of them are already in the audit (§5, §10).
- **The aiida-core wheel hash in `uv.lock` equals the reviewed artifact in `deployment/pins.json`:** `767e7714f3b95a17ee5c0d82c1bd2e1ea379ba3f5e1a2fa295894379296fc30c`. Today's dependency on a retired runtime's download folder (`old_runtime_root`) can therefore be replaced by a hashed install from the lock.
- **Neither source tree has package data.** There are no files other than `.py` under `application/src` or `integration/src`, so a wheel needs no include configuration for data files.
- **The build backend is the only new dependency.** Everything else in the task uses only packages and versions that the audit already approves.

### setuptools 84.0.0: contents that matter

- **Vendored in `setuptools/_vendor/`:**

  |---|---|---|
  | autocommand | 2.2.2 | **LGPL-3.0** (classifier "GNU Lesser General Public License v3") |
  | backports.tarfile | 1.2.0 | MIT |

  | jaraco.text | 4.0.0 | MIT |
  | jaraco.context | 6.1.0 | MIT |
  | jaraco.functools | 4.4.0 | MIT |
  | more-itertools | 10.8.0 | MIT |
  | packaging | 26.0 | Apache-2.0 OR BSD-2-Clause |
  | platformdirs | 4.4.0 | MIT |
  | tomli | 2.4.0 | MIT |
  | wheel | 0.46.3 | MIT |
  | zipp | 3.23.0 | MIT |

- **LGPL-3.0 conflict.** autocommand is not permissive, so under the dependency rule ("new dependencies must have permissive licences") it is a licence conflict that needs review. It runs only inside the isolated build environment. It does not end up in the built wheels or the native environment, and HYPRN MVP does not distribute setuptools.
- **Startup path file.** The wheel contains `distutils-precedence.pth`, which runs `_distutils_hack` at the start of every interpreter in any environment that setuptools is installed into. This is harmless in a throwaway build environment, but setuptools must never be installed into the native environment, because the acceptance check refuses any `.pth` file there.
- **Windows executables.** The wheel contains eight Windows launcher executables (`cli*.exe`, `gui*.exe`). They are unused on supported hosts.
- **No `pkg_resources`.** Version 84.0.0 no longer ships `pkg_resources`, and nothing in the checkout uses it.
- **Changes in the checkout:**
  - `integration/pyproject.toml`: `requires = ["setuptools==84.0.0"]`.
  - `application/pyproject.toml`: a new `[build-system]` with `requires = ["setuptools==84.0.0"]` and `build-backend = "setuptools.build_meta"`.

  The `src` layout is discovered automatically.

### flit_core 4.1.0: contents that matter

- **Contents.** `flit_core` itself and a vendored tomli 1.2.3 (MIT), which is used only on Python older than 3.11. There is no startup path file, no executable and no other vendored code.
- **Release history since 4.0.**
  - 4.0 is a new major series. It drops `[tool.flit.metadata]`, which the checkout does not use, because both projects use `[project]`.
  - 4.0.3 fixes wheels that were written 0600. This is relevant because `./hyprn-mvp` runs with umask 077 and the wheels are installed into an environment that the executor reads.
  - 4.1 accepts licence expressions with `WITH`.
- **Changes in the checkout.** Both `pyproject.toml` files get `[build-system] requires = ["flit_core==4.1.0"]` and `build-backend = "flit_core.buildapi"`. The module names `hyprn_mvp_app` and `hyprn_mvp_integration` equal the normalised project names, and flit finds `src/`.
- **To confirm in a scratch build after approval.** flit requires `version` and `description` statically or as `dynamic`, and `integration/pyproject.toml` has no `description`. One line would be added.

### uv_build 0.12.24: contents that matter

- **Embedded SBOM.** The wheel embeds a CycloneDX SBOM of the 259 Rust crates in the binary. All of them are permissive (MIT, Apache-2.0, BSD, Zlib, 0BSD, Unicode-3.0, CC0, BSL-1.0) except one, `astral-version-ranges` 0.2.2, which is **MPL-2.0** (file-level weak copyleft). The binary is not distributed.
- **Native binary.** A native executable runs at build time, and HYPRN MVP needs one artifact per host platform.
- **Changes in the checkout.** Both `pyproject.toml` files get `requires = ["uv_build==0.12.24"]` and `build-backend = "uv_build"`. The default module root `src/` and the module names match.

## How the pin would be applied (any option)

- **Build lock.** A build lock under `deployment/locks/` holds the backend's exact version and SHA-256 values.
- **Acquisition.** The backend artifact is acquired in the acquisition stage and verified by hash.
- **Build.** Each wheel is built offline in an isolated build environment, using `uv build --wheel` with the hashed build constraint and no index. The exact `uv build` flags are to be confirmed against uv 0.12.24 when the task resumes. The build reads from the snapshot, never from the checkout, and sets `SOURCE_DATE_EPOCH` to the snapshot's commit time so that the build is reproducible.
- **Install.** The wheels are installed into `execution/venv-<lock16>` with `--no-deps`. The backend is never installed there.
- **Recorded identities.** The built wheel hashes are recorded in the installed inventory.

## Options for the product owner

- **(a) setuptools 84.0.0.** This follows the wording of D6 (b) and STATE. It requires accepting the vendored LGPL-3.0 autocommand as a build-time-only residual: never shipped, never in the native environment.
- **(b) flit_core 4.1.0 (recommended).** It has the smallest surface: pure Python, BSD-3-Clause, no dependencies, no startup path file and no executables. It has a PyPI attestation, and its 0600 wheel permissions bug is fixed. It changes the backend named in STATE from setuptools to flit_core, so D6 (b) would be recorded as "pinned and audited build backend: flit_core 4.1.0".
- **(c) uv_build 0.12.24.** It comes from the same project and release as the audited uv, and it has an embedded SBOM. However, it brings a native binary per platform, one MPL-2.0 crate and no PyPI attestation.

Whichever option is chosen is copied into `docs/operations/dependency-audit.md` as a new section when task 2.5 resumes. Installing it then needs no further checkpoint.
