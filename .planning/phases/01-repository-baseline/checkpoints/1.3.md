2. **Served installations are named explicitly.** `ui/tests/support/served.ts` reads `HYPRN_MVP_UI_BASE_URL` (an http(s) origin, no credentials, path, query or fragment) and `HYPRN_MVP_UI_PASSWORD_FILE` (absolute path of the owner password file); neither has a default. `ui/playwright.config.ts` takes its `baseURL` from it, and its browser evidence goes to the scoped test folder or to `<evidence root>/ui` (`HYPRN_MVP_EVIDENCE_ROOT`, else `<data root>/evidence`); the previous fixed scratch evidence prefix is gone. 3. **Chromium, build output, data root.** `ui/tests/support/browser.ts` reads `HYPRN_MVP_CHROMIUM` (Playwright's own resolution when unset); `ui/vite.config.ts` builds into `ui/dist` unless `HYPRN_MVP_UI_OUT` is set. `ui/playwright.isolated.config.ts` (decision 1) runs the fixture guard with `HYPRN_MVP_NATIVE_PYTHON` as handed over resolved by the scoped fixture and passes exactly the scoped environment (key list of checkpoint 1.2, compared for equality by the guard). 5. **Compositions and names.** Isolated specs that no group ran were updated to the current screens and registered (`ui-reading`), or removed where every case targets superseded screens; spec files named after work streams were renamed after the behaviour they test; the one `approach-ui-controller` case was repaired (decision 2, below).

Registry (`deployment/checks.py`): new need `installation` (both served variables set); new groups `ui-reading` (must-pass, browser), `ui-fidelity` (opt-in, browser), `ui-served` (opt-in, browser + installation). `ui-served` validates the installation before allocating a scope: the URL must be an explicit loopback origin that is neither a live installation port nor `HYPRN_MVP_PORT`, and the password file must be an existing absolute, non-link file outside the development stores and every live root; it then runs the served specs with `ui/playwright.config.ts` in a fresh scope (environment: the scoped environment plus the two variables) and fails closed on zero, skipped, flaky or unexpected results. `browser_specs()` maps every registered browser spec to its groups (targets plus `FIXTURE_BROWSER_SPECS` for the spec the `units-native` fixture runs). `--list`: 99 groups (97 must-pass, 2 opt-in) + `qualification`.

## Decision 2: `approach-ui-controller` 1 of 17

Case "approach version page denial survives a version switch and late replies cannot repopulate". Cause (from the server call log of a failing run): opening the saved version also reads `…/approach/versions/<id>/usage`; the case revoked access before switching, so that read reached the service after the revocation, was denied, the client confirmed the denial with a study read (also denied) and correctly cleared the page — sometimes before the late version reply was rendered and observed, sometimes after. Not a product defect: clearing protected content on a confirmed denial is the required behaviour. Fix: the usage reply of that version is captured before the revocation, like the version reply, so the only denial the page can observe is the held page of versions. No assertion was removed or weakened.
