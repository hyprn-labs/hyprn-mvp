# Cloud native owner and Linux artifact continuation

This completes the scientific portion of 06-05 after the application/modeling
lifecycle prerequisite batch. It does not replace that plan's acceptance or mark
06-05 complete. Platform host startup remains dependent on both portions.

## Outcome

An isolated Linux amd64 installation initializes its own AiiDA store, verifies the
exact restricted worker and runs a representative real calculation through the
PostgreSQL dispatcher boundary. Saved joint sampling and validated predictions
retain their existing accuracy gates. No production installation is a fixture.

## Ownership and boundary

A fresh executor owns the minimal cloud execution adapter, native-owner lifecycle
wrapper, related source-closure pins and registered native/artifact tests. Reuse
`native_environment.prepare` and `initialize`, `NativeExecution`, the existing
launcher and platform-reviewed runtime bindings. Do not feed `runtime/v1` into the
local installation schema, fake a local origin, reuse development owner/profile
identities or bypass current worker attestation.

The cloud execution configuration is a narrow validated projection from pinned
platform runtime/release identity. It carries installation/store identity, exact
execution root, profile identity, reviewed Docker endpoint and native executable
paths. It has no database or provider credentials. Keep local configuration
behavior unchanged. Cloud selection must reject ambient local/development-root
overrides, rather than falling back to development owner or profile identities.
The private execution projection is generated by trusted host code and contains
only execution fields, not the full runtime document or credential references.
Any new module in the launcher's import closure must enter
its existing attested source inventory and require a fresh attestation.

Mutable execution data stays in the platform runtime's execution store. Linux
Python/native dependencies and source live under the immutable source-identified
release prefix. Existing hashed uv/CPython/native locks support Linux x86_64;
there is no need to invent package versions. A build on macOS is not the target
artifact. The parent can operate an isolated amd64 build after the executor
supplies the committed source revision and agrees the install prefix.

## Observable checks

- Build the pinned native environment in an isolated amd64 container. Include
  reviewed interpreter and dependency bytes, licences and source identities.
  Apply the existing shipped-interpreter policy from `install_python.py`: exclude
  the separate Sleepycat-linked `_dbm` extension (legal item L6) and bundled
  packaging tools, retaining the required Python notices. A locally downloaded
  interpreter is not automatically approved for redistribution unchanged.
- Platform bundle policy admits regular files/directories only. If flattening
  symlinks, first reject targets outside bundled roots, then prove the packaged
  interpreter and installed dependencies work after fresh extraction at the
  exact deployment prefix. A prepared venv alone does not prove portability.
- Explicit initialization refuses existing or foreign stores. Ordinary start
  never initializes/migrates. Profile/store UUIDs are checked, not names alone.
- Native operations carry real owner receipts consumed by the product lifecycle;
  missing/uncertain work remains closed and is never represented as success.
- Exercise PostgreSQL dispatcher discovery and per-job actor scope, real model
  execution, persisted results and restart/reconciliation. Verify worker cannot
  access network, metadata, database/provider secrets or host filesystem.
- Run the required registered native/artifact groups on exact committed source
  and packaged bytes; retain each failure and scoped cleanup. No source-only or
  mock-only substitute for installed-artifact acceptance.

Remaining outside this batch: platform host fencing/firewall/bootstrap, coherent
backup/restore, release publication, live cloud attestation and owner approval to
activate staging. These remain required for usable staging and automatic deploys.
