# Phase 3 — UI Design Contract

> Visual and interaction contract for the UI parts of Phase 3 (Agent tools for coding agents). Generated by gsd-ui-researcher, verified by gsd-ui-checker, revised for ADR-0002 (`docs/adr/0002-agent-write-rights.md`): agent writes execute directly and are attributed and journaled, so the earlier proposal page is replaced by a read-only **Agent activity** page; then revised for ADR-0003 (`docs/adr/0003-agent-write-rights-revised.md`, which supersedes ADR-0002: agents may also create studies, which the delegating user owns, and change or remove draft content under revision checks, while deleting saved records, archive and restore, and access management stay human-only) and ADR-0004 (`docs/adr/0004-operation-ownership.md`: the page shows the outcomes the platform recorded and never reconstructs or repeats an operation to display it). Every value below is a token from `design-system/tokens.json` or an existing `ui/src/design` component; this contract adds no new visual language.

**Scope (UI only).**

1. **Attribution chip** — "{agent} for {user}" wherever an agent-written record, version, run or receipt is shown, including a study an agent created, on Home and in its study heading (D-02, D-17; AGENT-05; tooling spec §3.1, §3.3; ui-target §4.4). Delivered in stage 1 (agent principal and attribution).
2. **Agent activity page** — a study-scoped, read-only page listing what the signed-in user's agents did in the study, newest first, from the action journal: the agent attribution, the operation in plain language, the outcome, guard warnings and links to the records created or changed; plus the agents' current access to the study, with "Revoke access" as the way to stop an agent and the command-line renew command (D-17; AGENT-06, AGENT-07, UI-04; ui-target §4.4; tooling spec §3.3, §3.4). Delivered in stage 3; stage 4 adds configuration, run-submission and conclusion entries with no UI change.
3. **Agent status surfaces** — assistant access turned off (kill switch, D-11), assistant access ended (revocation, expiry, membership change), and the human's own access loss on this page (AGENT-07; tooling spec §3.5, §6.4).

**Out of scope.** A separate token-management panel (PD-3.5 as amended: tokens are listed through the CLI and the owner-session API, and revoked there or from this page); the cloud assistant panel, Stop control, spend display and conversation (tooling spec Stage 4); progress-note and platform-issue lists (Open question 15). Agents have no proposal, confirmation or approval UI: ADR-0002 retired it and ADR-0003 keeps it retired. Agent-recorded scientific reviews are out of scope until the review record exists (their chip and the label "Recorded by an assistant" are listed below for that later work).

**Binding sources used.** `AGENTS.md`; ADR-0003 (superseding ADR-0002) and ADR-0004; `03-CONTEXT.md` (D-02, D-04, D-09, D-11, D-17, D-18, PD-3.5, planner's discretion on page layout); `docs/specs/ui-target.md` §1, §2, §3.1, §4.4, §5, §7; `docs/agents/tooling-spec.md` §2.5, §3.1–3.5, §4.9, §4.11, §6.4, §7.1, §10.2, §10.3, §12; `docs/specs/agents.md` §3; `docs/specs/requirements.md` UI-03, UI-04, AGENT-05–08; `design-system/README.md`, `Layouts.md`, `Scientific-states.md`, `Naming.md`, `Coherence.md`, `components/*.md`; `ui/src/design/*`; the study shell and link model in `ui/src/Workspace.tsx` and `ui/src/workspaceModel.ts`.

## Surface 1 — Attribution chip

### Anatomy (`AttributionChip`)

- Props: `agent: string` (agent display name, e.g. "Codex (local)"), `user: string` (delegating user's display name), `className?: string`.
- Renders inline: `[iris mark] {agent} for {user}`.
- Mark: a solid `ai` square, `radius-xs`, with the iris glyph in `on-ai`, sized like the `StatusTag` mark (fixed measurement in `foundry.css`), `aria-hidden`.
- Text: `small` (12/16, 400), `ink-2`; the word "for" in `ink-muted`; names in `ink-2`.
- Box: `surface` ground, 1px `line` border, `radius-xs`, padding 2px `space-2`, gap `space-1` — the `StatusTag` geometry with a neutral tone, so it reads as metadata, not status.
- Wrapping: `white-space: normal`, `min-width: 0`, `overflow-wrap: anywhere`. Names are never truncated (truncation would hide who acted).
- Accessible text: a visually hidden prefix "Assistant: " before the agent name (class `hf-visually-hidden`), so screen readers read "Assistant: Codex (local) for {user}". Not focusable, not interactive.
- Agent and user names are untrusted text: rendered as plain text by React, never as markup or links.
- The UI composes the text from two separate API fields (agent display name, delegating user). It never parses a combined string and never doubles "for" (Open question 10).

### Rule

A chip is shown when, and only when, the record's receipt actor is an agent. Human-authored records show no chip: absence means a person did it ("normal is the absence of a tag"). The chip names who acted and nobody else: agent writes are direct (ADR-0003), so there is no confirmer. Historical views read the attribution stored with that version or run, never a current name.

### Placements (one chip per record per screen; Coherence rules 2 and 6)

| Record | Where the chip appears | Position |
|--------|------------------------|----------|
| Study an agent created | Home study rows (from the Home attribution read); the study heading row of that study | End of the Home row's metadata; after the study title in the heading row |
| Study context change (description) | Overview › About this study, after the description | A `small` line under the description: chip only, when the current description was last written through an agent |
| Evidence version | Evidence › Sources rows; View evidence dialog (version line); evidence picker rows | End of the row's metadata line; after the version line in the dialog |
| Model version | Model heading row of a saved version (beside "Read-only model version"); model version select is unchanged | After the state tag |
| Model draft | Model heading row of the draft (beside "Draft · saved") when the latest draft revision was written by an agent | After the state tag |
| Approach draft and approach version | Modeling approach header, beside the draft status tag or the version select | After the tag |
| Configuration version | Configuration heading row (beside "Saved · read-only"); configurations list rows; Overview recent configurations rows | After the state tag; end of the row metadata |
| Run | Run detail heading context line; run history rows; Overview recent runs rows; case cards' run rows | In the `small` metadata, before the Execution and Criteria tags (tags stay at the right end, StatusTag rule) |
| Agent activity row and agent access row (Surface 2) | Metadata line of each row | First item of the metadata line |
| Scientific review recorded by an agent (later, once the review record exists; nothing is built in this phase) | Wherever the review is shown | Chip plus the label "Recorded by an assistant" (ui-target §4.4) |

Agents never delete saved records, archive or restore anything (ADR-0003), so no lifecycle row carries a chip. Draft content an agent removed shows through the draft's own chip, because the draft's latest revision was written through the agent.

**Record details** (every record dialog above) gains one row, only for agent-written records:

| Label | Value |
|-------|-------|
| "Saved by" (versions, evidence, configurations) · "Submitted by" (runs) · "Changed by" (drafts, study context) | "{agent} for {user}" |

The run sentence from the tooling spec appears verbatim as the Record details summary line of an agent-submitted run: "Submitted by {agent} for {user}".

## Surface 2 — Agent activity page

### Route and entry

- **View:** a study-scoped view `activity`, added to `WorkspaceView` and `parseWorkspaceLink`, with no resource key. Link: `#v=1&view=activity&study=<study id>`; after sign-in the browser returns to it like every deep link. A resource key given with `activity` is an invalid link.
- **Not a sixth study tab.** The study tabs stay Overview, Models, Configurations, Runs, Evidence (Layouts.md, Naming.md fixed labels). On this view no study tab carries `aria-current` (the study tabs are navigation buttons; all stay reachable). Precedent: the modeling approach is a study view without its own tab.
- **Entry point:** a `quiet` button "Agent activity" at the right end of the study heading row (same row as the study `title`), always shown inside a study, with no count. See Open questions 2 and 3.
- **Breadcrumb:** `/ {study} / Agent activity`.
- **Editor guard:** navigating to this view goes through the existing editor guard (Save / Discard / Keep editing).

### Page composition (top to bottom, inside the shell's content column, `page-max`, `page-gutter`)

1. Study heading row (shell) with the entry button; study tabs (shell), none current.
2. `SectionHeader` level 2: "Agent activity", with a `quiet` "Refresh" action on the right.
3. Intro, `body` `ink-2`: "What assistants working for you did in this study, newest first. Assistants save versions, evidence, configurations and runs, and can start new studies, each marked with who acted. They never delete saved work, archive or restore anything, or change who has access."
4. Agent status notices, if any (Surface 3), `space-4` apart.
5. `Panel` "Agent access" (below).
6. `Panel` "Activity": the `Tabs` segmented switch (label "Activity view"): "Changes" · "All calls"; then the list; then, on "Changes", the hidden-reads line; then "Show more activity" while more exist.
7. Footer (shell).

### Activity list

- A `ul` labelled "Agent activity: changes" or "Agent activity: all calls"; one `li` per action, a 1px `line` hairline between rows (the Runs list pattern), `space-3` vertical padding.
- **Order:** newest first by start time; 25 per read; `quiet` "Show more activity" at the end while more exist. Refresh reloads the first page; a polite status announces "{N} new actions." ("1 new action.") when the first page holds actions that were not shown before. The page does not poll.
- **Changes** (default): every write (any effect other than read), plus every call whose outcome is not Completed — refused, failed, uncertain or in-progress calls, reads included. Below the list, when completed reads were left out: `small` line "{N} read calls are not listed here. Show them under All calls." ("1 read call is not listed here. …").
- **All calls:** every call, including completed reads.
- Progress notes and platform-issue reports appear by operation only ("Progress note", "Platform issue report"), never with their text.

### Activity row anatomy

1. **Operation line** (`body-strong`, `ink`): the API's `operation` text, verbatim (table below); the outcome `StatusTag` at the right end of the line (StatusTag rule).
2. **Metadata line** (`small`, `ink-muted`, wraps): `AttributionChip` · "{YYYY-MM-DD HH:mm}" (start time) · `ActionDialog` "Record details" (`sm`).
3. **Reason line** (refused, failed, uncertain and in-progress only; `body`, `ink-2`): from the outcome table, with the API's reason message.
4. **Warnings** (only when present): one line per warning, `StatusTag warning` "Warning" followed by the warning text as given (plain text), `space-2` apart.
5. **Record links** (only when the call created or changed records): `quiet` link buttons, one per record, named by the record-link table, `space-2` apart, wrapping.

All text from the API (operation, names, reason messages, warnings) is rendered as plain text; nothing is auto-linked, no markup is interpreted, and long text wraps (`overflow-wrap: anywhere`).

**Record details** dialog "Agent action record" (a `dl`, the existing record-details pattern): "Action ID", "Tool", "Effect" ("Read", "Draft", "Record", "Run submission", "Outside the study"), "Agent" ({agent} for {user}), "Started", "Finished", "Outcome", "Reason code" (when present), "Command ID" (one per command), "Request ID" (one per API request), "Argument SHA-256". Full IDs and SHA-256 values in `code`, copyable.

### Outcome words and tones (`StatusTag`)

| Outcome (API) | Tone and mark | Tag word | Reason line |
|---------------|---------------|----------|-------------|
| `completed` | ok, filled circle | "Completed" | none |
| `in_progress` | running, turning ring (static under reduced motion) | "In progress" | "Still in progress. Refresh to see the outcome." |
| `uncertain` | warning, triangle | "Outcome uncertain" | "The outcome of this call is not known. Don't resubmit; check the records before making more changes." For run submissions: "Submission outcome is uncertain. The runs are never submitted again automatically. Check the run history before making more changes." |
| `refused` | warning, triangle | "Refused" | "Refused: {reason message} Nothing was changed." |
| `failed` | alarm, filled diamond | "Failed" | "Failed: {reason message} Nothing was changed." |

Rules carried by the outcomes:

- "Completed" is the stored outcome of the tool call only. It never stands for a run's execution or criteria; runs an agent submitted show their own Execution and Criteria tags on their own pages (Scientific-states.md), not on the activity row.
- "Refused" means HYPRN MVP refused the call and nothing changed: a limit, the kill switch, ended access, a guard block, invalid input, readiness, a configuration not ready to run, an overwrite conflict that kept another person's change, or a route agents may never use (deleting saved work, archive, restore, access). It is a warning, not an alarm: the control worked, and the reader may need to act.
- "Failed" means the call was attempted and did not complete for another reason; nothing changed.
- The page never re-sends anything an agent did; it only reads. An uncertain outcome is an explicit warning, never a running track (Scientific-states.md).

- Lists each agent of the signed-in user that currently has access to this study (from the access read), one row each, a hairline between rows:
  - Line 1: `AttributionChip` "{agent} for {user}"; at the right end, for the study Owner, `secondary` "Revoke access" (accessible name "Revoke access for {agent}").
  - Line 2 (`small`, `ink-muted`): "Access until {YYYY-MM-DD HH:mm}" · "This session: {N} of 600 API calls · {R} of 60 runs submitted · {Q} of 10 runs waiting or running", or "No open session." when the agent has none.
  - A viewer who is not the study Owner sees no button (absent, not disabled) and a `small` line "Only the study Owner can revoke access."
  - Under OQ-1 option C (no owner-session routes) the button is replaced by the command `./hyprn-mvp mcp token revoke --study {study ID}` in `code` with "Copy command".
- **Empty:** "No assistant has access to this study." When no "Access ended" notice is shown, it continues: "Give a coding agent access from the command line:" followed by `./hyprn-mvp mcp token renew --study {study ID}` in `code` and a `secondary` `sm` "Copy command".
- **Access read error:** inside the panel, `role="alert"`: "Agent access could not be loaded. {API message}" with `secondary` "Retry"; the panel never says that no assistant has access when it could not read the access state.

### Revoking access

- "Revoke access" opens a modal `DialogFrame` titled "Revoke access for {agent}?" with the body: "{agent} for {user} loses access to this study at its next call. Everything it already saved stays, and runs it submitted keep running. To give it access again, renew it from the command line:" then the renew command in `code` and a `secondary` `sm` "Copy command". Footer: `danger` "Revoke access" and `secondary` "Cancel". Initial focus on "Cancel"; Escape cancels and sends nothing.
- Confirming sends one revoke request with the browser session and its cross-site request token. On success the dialog closes, the agent leaves the access panel, its "Access ended" notice appears (reason revoked), focus moves to that notice (programmatic target, `tabIndex=-1`), and a polite status says "Access revoked for {agent}."
- An error keeps the dialog open with `role="alert"`: "Could not revoke access. {API message} The assistant still has access."
- A lost response re-reads the access state (never re-sends automatically). If the access has ended, the page proceeds as on success; otherwise the dialog shows "The outcome of the revocation is not known. Check again before trying again." with `secondary` "Check again"; pressing "Revoke access" again reuses the same command ID.
- Revoking ends the assistant's access to the study; it is not run cancellation and changes no study record.

## Interaction and keyboard

- Every action has a keyboard path; focus is always visible (2px `focus` outline, offset 2px).
- Tab order on the page: entry button (shell) → study tabs → Refresh → notices' "Copy command" → Agent access rows' "Revoke access" (or the empty state's "Copy command") → segmented tabs (Left/Right/Home/End switch segments) → each row in list order: Record details → record links → "Show more activity".
- Rows themselves are not focusable; the operation line is plain text. The revoke dialog and Record details dialogs restore focus as described.
- After "Show more activity": focus stays on the button (now after the new rows) and a polite status says "{N} more actions loaded." ("1 more action loaded.").
- Revoke dialog: modal `DialogFrame` with focus wrapping, initial focus "Cancel", Escape closes; after a cancel, focus returns to the "Revoke access" trigger; after a success, to the new "Access ended" notice.
- Record details dialog: `ActionDialog` behaviour (focus restore to its trigger).
- No keyboard shortcut revokes anything; Enter and Space activate the focused button only.
- Status changes are announced politely (`role="status"`); errors use `role="alert"`.

## Themes, zoom and motion

- **Light and dark:** tokens only; verify every outcome tag, both notices, the access rows, the dialog and the chip in Day and Control room. The chip on `surface`, the `advisory` tags on `advisory-soft`, and the `warning` and `alarm` tags on `surface` must meet the contrast stated in `tokens.json` in both themes.
- **Genuine 200 % browser zoom** at the 1440 × 1000 reference (720 CSS px wide) and at 1024 px width, both themes: no horizontal page scroll; the operation line, metadata line, warnings, record links and access rows wrap; long tag words and the chip wrap (no `white-space: nowrap`); the renew command wraps inside its well; the revoke dialog fits and its buttons stay reachable; "Revoke access" and "Show more activity" stay reachable without horizontal scrolling. Below 600px every row and action group stacks to one column (Layouts.md). A 720px viewport is reflow evidence only and is never recorded as genuine zoom.
- **Reduced motion:** the `running` mark is static; no motion is added.
- **Touch:** controls switch to `control-floor` (48px) as elsewhere.

## Open questions for the product owner

Each has a recommended default that this contract already applies; none is presented as settled by the sources. Numbering is kept from the first version of this contract; retired questions stay listed.

1. **Proposal action and status words.** Retired by ADR-0002 and kept retired by ADR-0003: agents have no proposals.
2. **Placement of the Agent activity page.** Layouts.md fixes five study tabs and no source places the page. **Default:** a study-scoped view reached from a quiet "Agent activity" button in the study heading row; no sixth tab; no tab marked current on the page.
3. **Visibility of the header entry.** **Default:** always shown inside a study (the empty state explains assistants and how to give one access), with no count. Alternative: show it only once the study has had an agent delegation, or add a warning count for uncertain outcomes.
4. **Attribution chip as a new design-system component.** **Default:** new `AttributionChip` in `ui/src/design` with its own component note, because the assistant mark is not exported and screens may compose only from design-system exports. Alternative: export the iris mark and compose in screens (rejected: a second presentation of the same concept on many screens).
5. **Outcome words and tones.** **Default:** "Completed" (ok, the stored outcome of the call only), "In progress" (running), "Outcome uncertain" (warning, "don't resubmit"), "Refused" (warning: the control worked and nothing changed), "Failed" (alarm). Alternative: "Refused" as alarm.
6. **Batch semantics.** Retired by ADR-0002 and kept retired by ADR-0003: nothing is confirmed in batches.
7. **Confirmation before revoking access.** **Default:** a dialog naming the agent, the consequence and the renew command, with `danger` "Revoke access" and `secondary` "Cancel" (initial focus). Alternative: revoke directly from the row.
8. **Command line and full study ID in the "Access ended" notice and the revoke dialog.** ui-target keeps full IDs in Record details, but renewing access is a CLI operation that needs the study ID. **Default:** show the renew command with the full study ID in `code` and a "Copy command" button, local edition only.
9. **Which actions the page lists.** **Default:** only actions made under the signed-in user's own delegations; in the local edition that is the Owner's agents.
10. **API data the UI needs (planning dependency).** Separate agent display name and delegating-user fields; a closed outcome enum with a reason code and HYPRN MVP message; the records created or changed, with their kinds, IDs and names as stored at write time; installation agent access (kill switch), per-agent access state with expiry and session usage; the token IDs that revocation needs. **Default:** the planner adds these to `contracts/hyprn-mvp.openapi.yaml` (tasks 3.4 and 3.22); the UI never parses names or infers states from error text.
11. **How far back the activity goes.** **Default:** everything the API returns, newest first, 25 per read.
12. **Kill-switch remedy copy.** **Default:** "It is turned on again in the installation configuration." without naming the setting or the environment variable in the UI.
13. **Expiry display.** **Default:** the absolute access expiry ("Access until {YYYY-MM-DD HH:mm}"); no countdown and no "expiring soon" warning; the server decides expiry.
14. **Token list and revoke in the UI.** Resolved by OQ-1 (option A, recorded at checkpoint 3.2) and the amended PD-3.5: revocation is offered on this page through the owner-session revoke route; tokens are listed through the CLI and the owner-session API; no separate token-management panel this phase.
15. **Progress notes and platform-issue reports.** The tooling spec decides an in-app list of platform-issue reports for the Owner; Phase 3's context does not schedule it. **Default:** not built in this phase; the activity list names such calls without their text; recorded as remaining UI debt in ui-target §7.
16. **Reads in the activity list.** An agent makes many read calls. **Default:** completed reads are hidden in "Changes" (the default view) with a count, and listed in "All calls"; refused or failed reads stay visible in "Changes".
