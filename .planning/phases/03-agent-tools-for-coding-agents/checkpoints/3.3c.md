## What was built

- **One run-row read (cecd959).** `history.run_association(db, run_id, *, study_id=None, payload=True)` holds the only `run_associations … JOIN outbox` row read outside the run-list projection; `payload=False` selects no payload bytes. `History.run_row` authorizes, then uses it (same columns, so row digests and tokens are unchanged). `execution`: `Submissions.read` and `hydrate` read through `History.run_row`; `_record`, its in-transaction re-read and `dispatch` through `run_association`; `execution` keeps only the association insert and the native-identity update. `ResultBindings.inventory` takes its high-water position and position range from `history.last_run_position` / `runs_by_position` in its own transaction after its own `authorize`. `Approaches.usage` keeps its configuration half and takes its run half from `history.approach_runs`; each half is SQL-bounded (`LIMIT limit+1`), configurations first, then runs, ordered by id, with the `(kind, resource_id)` cursor semantics unchanged. Boundary row `test_run_association_reads_have_one_owner`: outside `store` and `history`, the only statements naming `run_associations` are the reviewed writes of `execution`. No import edge added.
- **Acceptance time.** `run_associations.accepted_at TEXT` (nullable) in the schema DDL and in the existing additive migration block of `Store.__init__` (three lines); `Submissions.submit` writes it (UTC, microseconds, `Z`) in the acceptance transaction; nothing updates it. Receipts and outbox payloads carry no acceptance time.
- **`History.status(actor, sid, run_ids)`** and **`GET /api/1/studies/{study_id}/run-status?run_id=…`** in `routes/runs.py` (endpoint `light_run_status`): one authorization; 1–20 distinct canonical run ids, otherwise `invalid_request` 400 (also for any other query field or no `run_id`); scoped `resource_not_found` 404 with no partial answer when any id is not a run of the study; one statement over the association, outbox state and `json_extract`/`json_type` paths; configuration name from the run list's projection. `RunStatus1` per run, in request order: `run_id`, `configuration_revision_id`, `configuration_name`, `state`, `process_state`, `exit_status`, `facets` (execution, convergence, optimization, completeness, applicability) and `criteria`, each `{value, reason}` with `reason: not_recorded` while there are no retained results, and `times` with `submitted_at` (`not_recorded` when the row has no acceptance time) and `started_at`/`finished_at` always null with `not_projected`.
- **Contract.** `generate_contract.py` adds `RunStatus1` (facet and criteria schemas deep-copied from `RetainedResults`, `process_state`/`exit_status` from `PublicRun`), the `/run-status` branch (array `run_id` parameter, 1–20, unique, uuid) and the operation note of the plan. `contracts/hyprn-mvp.openapi.yaml` and `ui/src/contract.ts` were regenerated with `application/generate_contract.py` and `ui/generate_types.py`, never edited by hand.
- `deployment/checks.py`: `application/tests/test_run_status.py` added to `api-a` (additive). `docs/specs/architecture-and-contracts.md` §11 open question 5 states the delivered read and that process times stay open.
- **Deviation (Rule 3, files outside the task's list):** `application/tests/test_study_archive.py`, `test_computational_records.py` and `test_approach_service.py` inserted run-association rows positionally (`VALUES(?,?,?,?,?,?)`), which a seventh column breaks; 20fd629 names the six columns. Rows, assertions and counts are unchanged (groups `api-a`, `archive-service`, `approach-service`, and `api-c`/bridge fixtures that import `retain`).
