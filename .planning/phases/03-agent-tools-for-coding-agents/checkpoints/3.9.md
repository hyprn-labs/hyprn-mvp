## Practice decisions and differences from tooling spec section 4

D-P5 (one effect, one owner set, no `action` multiplexing), D-P6 (description pattern, closed bounded schemas), D-P7 (all four hints), D-P9 (fixed list in registry order; `TOOL_DEFINITIONS_SHA256` changes only with the catalogue) and D-P10 (`get_study_overview` and `get_playbook` always load) apply. No split or merge of section 4 tools. Differences, none from a D-P decision:

1. Input names: `get_model` and `get_assumption_evidence` take `which` plus `model_version_id`, `get_approach` takes `which` plus `version_number`: the registry's OQ-6 rule refuses a field named `version`.
2. `check_execution_readiness` reports the owner's words `ready | unavailable | unknown`; `get_run_status` reports the owner's `state` and no `phase` or `stalled` (no derived state; stall detection belongs to `wait_for_runs`, 3.32).
3. `list_configurations` has no `case_id` filter or run counts and `list_runs` no `configuration_id` filter: the owners' lists have no such filter and the configuration row declares no run read; `get_approach_usage` answers which configurations and runs implement a case. `list_evidence` maps `view: all` to the owner's `versions`.
4. The overview's row has no model draft read, no capability read and no status read: models are a count with a pointer to `list_models`, the latest runs carry their state, capabilities point to `get_capabilities`.
5. Model versions are numbered by position in the owner's stored insertion order (its contract states that order). Superseded-pin warnings arrive with `edit_model` (3.26).
6. The `untrusted_content` author is "study member": the reads carry no attribution yet (3.6, 3.7).
