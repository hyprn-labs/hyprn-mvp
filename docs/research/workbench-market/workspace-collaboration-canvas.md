# Workspace, collaboration, documents and canvas foundations

Research date: 2026-10-12. Part of the workbench market study; the synthesis is in [recommendation.md](recommendation.md). Research input, not a decision; nothing was installed.

## Method and evidence rules

- Licences were read from each repository's current licence file through the GitHub API on 2026-10-12 (`gh api repos/<repo>/license`, plus the licence files inside `ee/`, `enterprise/` and per-package directories where they exist). Licence-change dates come from the commit history of the licence file. npm licence fields and React peer ranges were read with `npm view` on the same day.
- "Last release" and "last push" are GitHub API values on 2026-10-12. Contributor counts come from the GitHub contributors endpoint, which includes anonymous contributors, so read them as rough numbers.
- Vendor pages were fetched on 2026-10-12. Anything not confirmed from a primary source is marked **(unverified)**.
- HYPRN MVP constraints applied: all clients go through the HYPRN MVP API; the UI is custom and independently implemented (design-system tokens, no external fonts or URLs); the Python application owns authentication, studies, documents and assessments; WhatsOpt is the only editable composition graph (no second editable graph, so a node canvas must never become an editable model store). The UI runs on **React 19.3**, so React 19 peer support was checked.
- Licence verdicts: **Qualifies** = permissive (MIT, BSD, Apache-2.0, ISC) with nothing essential paywalled. **Weak copyleft** = MPL-2.0 or EPL-2.0, flagged separately. **Fails** = AGPL, GPL, BSL, source-available, licence key, or open core with the needed feature paywalled.

## 7. Recommended stack per category

### Identity and organisations: Keycloak (Organizations) behind HYPRN MVP, with Authlib in FastAPI

Keycloak is the only fully Apache-2.0 option whose organizations, invitations, per-organization identity-provider brokering (enterprise SSO), MFA and admin console are all in the open-source build, with a large contributor base and foundation backing. FastAPI stays the session owner: it runs the OIDC code flow with Authlib, then issues its existing cookie and CSRF. Clients therefore keep talking only to the HYPRN MVP API, and HYPRN MVP still authenticates clients and authorizes operations.

Keep workspaces, study memberships and workspace invitations as HYPRN MVP domain records. Use Keycloak organizations only for tenant, SSO-domain and identity concerns, so memberships are not owned twice. Theme the login pages with Keycloakify (MIT) using design-system tokens.

- Effort saved: SSO, SAML and OIDC brokering, MFA, password reset, account recovery and enterprise identity-provider onboarding. That is several engineer-months, and security-sensitive.
- Lighter alternative: Casdoor (Apache-2.0, Go), after a CVE review.
- Main risks: operational weight (a JVM service, its own Postgres schema, upgrades) and moving credentials out of the Python application, which changes the architecture's credential ownership and is a product decision. Splitting membership truth between Keycloak and HYPRN MVP is the main correctness risk.

### Authorization: OpenFGA, adopted only when sharing becomes hierarchical

Today's owner, writer and reader study memberships are well served by HYPRN MVP's own tables. Once the hierarchy becomes organization → workspace → study → document or comment, with inherited roles and per-object sharing, OpenFGA (Apache-2.0, CNCF Incubating, official Python SDK, Postgres) gives a tested ReBAC model plus list-objects queries. SpiceDB is the technically strongest alternative; Cerbos suits pure attribute rules.

Recommendation: define a `can(user, relation, object)` seam in the Python application now, backed by SQL, and swap in OpenFGA behind it when inheritance arrives.

- Main risk: dual writes (HYPRN MVP records and FGA tuples) drifting. Mitigate with an outbox from the authoritative HYPRN MVP transaction.
- Do not use Permify (relicensed to AGPL on 2025-05-12) or Oso OSS (deprecated).

### Real-time collaboration and authored documents: Yjs, Tiptap core, and a pycrdt-websocket sync endpoint in the Python application

Yjs gives shared state plus the **awareness protocol for presence** (who is in the workspace or study, cursors, selections), all under MIT. Tiptap core (MIT, headless, React 19) on ProseMirror with `@tiptap/extension-collaboration` gives the document editor, styled purely with design-system components.

Serve sync from Python with pycrdt-websocket (MIT, Yjs-compatible, the engine of Jupyter collaboration) mounted beside FastAPI. The existing session, CSRF and origin checks, study authorization and audit then apply to the socket, and document snapshots persist in HYPRN MVP's own store (Postgres later), keeping documents owned by HYPRN MVP. Hocuspocus (MIT, Node) is the fallback if scale or features outgrow pycrdt-websocket.

Build comments, review threads and resolution as HYPRN MVP domain records anchored with Yjs relative positions. Tiptap's comments, history, tracked changes and import/export are paid platform features, and Liveblocks is SaaS with an AGPL server.

This applies to authored documents (reports and memos written in the app). Uploaded source documents are stored and versioned on AiiDA, not in Yjs or Tiptap.

- Effort saved: the CRDT, merge, offline and presence engine, plus the editor. These are the hardest parts to build.
- Main risks: pycrdt-websocket's small maintainer pool (about 17 contributors) and the need to write a Postgres store. Mitigate by keeping the wire protocol standard Yjs, so swapping to Hocuspocus changes only the server. Avoid `y-redis`, which is AGPL.

### Canvas: xyflow, plus dagre (or ELK.js if accepted)

xyflow is MIT, company-funded, supports React 19 and renders DOM nodes, so design-system components work inside nodes. It suits study canvases: linked records, evidence, run lineage, and read-only or projected views of WhatsOpt compositions. Layout comes from `@dagrejs/dagre` (MIT), or ELK.js for better layered layouts if EPL-2.0 used unmodified is accepted. Add Excalidraw (MIT) only if a freeform whiteboard is a real requirement. Do not use tldraw: it is proprietary, needs a licence key and forbids production use without one.

- The main risk is architectural, not licensing: a node canvas easily becomes a **second editable model graph**, which the architecture forbids. Canvas edits must dispatch HYPRN MVP commands that go through the Modeling Backend Contract to WhatsOpt, never mutate a local graph. Do not adopt Rete.js for the same reason.

### Workbench layout: dockview core (MIT), pinned, with FlexLayout as the named fallback

dockview's free core already covers a dockable study workbench: tab groups, nested splits, floating and popout panels, serialisable layouts per user and study, custom tab renderers, and CSS-variable theming that maps cleanly to design-system tokens. It has zero dependencies and supports React 19. Use react-resizable-panels (MIT) for the fixed shells (home, settings) that do not need docking.

- Main risk: **licence drift.** Since 2026-07-07 dockview has a proprietary, licence-keyed `dockview-enterprise` package. Keyboard docking, edge auto-hide and dock-to-edge, layout history, and pinned and multi-row tabs are now paid, and future features may land only there. Mitigate by:
  - pinning the MIT packages;
  - wrapping dockview behind one HYPRN MVP `WorkbenchLayout` component so screens never import it directly;
  - building keyboard docking ourselves if accessibility needs it;
  - keeping FlexLayout (MIT, Caplin; edge "borders" included) as the swap-in.
