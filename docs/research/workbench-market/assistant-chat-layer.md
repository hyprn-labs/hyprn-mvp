# Assistant chat layer and agent-to-UI protocols

Research date: 2026-10-12. Part of the workbench market study; the synthesis is in [recommendation.md](recommendation.md). Research input only: nothing here authorizes adoption, dependency installation, provider accounts, egress changes or implementation. All licences were read from the repository's current LICENSE file through the GitHub API on 2026-10-12 unless stated otherwise; npm and PyPI versions and dates were read from the registries the same day.

Scope: the in-study assistant panel of the HYPRN MVP workbench (HYPRN MVP screens, a chat panel and a canvas), the wire protocol between HYPRN MVP's backend and that panel, and the two provider-hosted runtimes under consideration (OpenAI and Anthropic managed agents). Local use through the Codex and Claude Code desktop apps over MCP is covered only where it touches the UI layer; the tool layer itself is specified in `docs/agents/tooling-spec.md`.

Criteria: (1) no duplication of WhatsOpt, AiiDA or OpenMDAO capabilities; (2) permissive open-source licence with unrestricted commercial use; (3) genuine delivery acceleration against building it ourselves; (4) neutrality between OpenAI and Anthropic managed agents.

## 1. Summary

- **Recommended combination.** HYPRN MVP keeps owning the tool registry, proposals, confirmations and journal (`docs/agents/tooling-spec.md`). The backend runs one thin binding per managed runtime (Claude Managed Agents, OpenAI Agents API) that exposes HYPRN MVP tools as **client-executed custom or function tools**, not as a remote MCP server. The backend re-emits each session as **AG-UI** events on HYPRN MVP's own authenticated, same-origin SSE endpoint. The panel is built with **assistant-ui** headless primitives (MIT) and its AG-UI runtime, rendered with HYPRN MVP design-system components, including proposal cards that confirm through HYPRN MVP's own `POST /api/1/agent/proposals/{id}/confirm`.
- **Do not adopt** OpenAI ChatKit for the panel. Its UI is a closed bundle loaded from `cdn.platform.openai.com`, and it needs an OpenAI-registered `domainKey` even with a self-hosted server. That breaks the design-system rule against external URLs, rules out HYPRN MVP components inside messages and ties the panel to one provider.
- **Licence-disqualified:** Open WebUI (branding clause above 50 users) and LobeHub/LobeChat (derivative works need a commercial licence). Onyx is MIT outside its `ee/` directories (open core) and is reference-only. LibreChat (MIT) is a whole application and is useful as a reference, not a base.
- **Both managed runtimes are beta, and neither is eligible for zero data retention.** Both stream over SSE using a server-side API key, both let the application execute custom tools, and both can be driven without built-in shell or web tools. Their event models differ, so an adapter layer owned by HYPRN MVP is unavoidable. That layer is small, and an MIT AG-UI adapter for Claude Managed Agents already exists.
- **Provider approval features are not a substitute for HYPRN MVP confirmations.** Claude's `always_ask` policy does not apply to custom tools, and the OpenAI Agents API pages read for this study document no approval primitive for function tools. The proposal → confirm flow stays in HYPRN MVP, which is also what makes it provider-neutral.

What this means for HYPRN MVP:

1. **Both runtimes support the pattern the tool layer needs.** HYPRN MVP's registry runs in-process as custom or function tool handlers, so the delegated session, CSRF, scope injection, guards and journal never leave HYPRN MVP. The provider sees only tool names, schemas and projections.
2. **Avoid remote MCP from the provider to HYPRN MVP for the in-app assistant.** It would require a publicly reachable HYPRN MVP MCP endpoint (OpenAI `connection_origin: service`) or a research-preview tunnel (Anthropic), plus OAuth for the provider, and it would move tool execution outside the browser-session-bound delegation. Keep MCP for the local-client adapter.
3. **Switch off sandboxes and built-in tools.** Use OpenAI `environment: none`. On Anthropic, set the toolset's `default_config.enabled: false` and use limited networking. This honours "no shell, filesystem, browser or web tools" and the no-duplication criterion: model execution stays in the attested worker through AiiDA.
4. **Proposals return immediately.** A C1 or C2 tool replies at once with `awaiting_confirmation`. The confirmation outcome is injected later as a new user or system event, so the provider session is not left blocked. Holding the tool call open until the human confirms also works on both runtimes, and idle time is unbilled on Anthropic, but it ties confirmation latency to provider session state.
5. **The provider stores the transcript.** Neither runtime is eligible for zero data retention, and OpenAI is US-only. HYPRN MVP therefore deletes provider sessions through the API in step with its own 90-day transcript retention, and confirms retention and region settings before a cloud pilot.

## 5. Recommended combination

```text
Browser (study workbench)
  HYPRN MVP screens + canvas + assistant panel
  assistant-ui primitives styled by ui/src/design (design-system tokens)
  runtime: @assistant-ui/react-ag-ui  (or ExternalStoreRuntime fed by HYPRN MVP state)
  tool-result renderers = HYPRN MVP components (projections, run tables, ProposalCard)
  ProposalCard "Confirm" → POST /api/1/agent/proposals/{id}/confirm (human session + CSRF)
        ▲  AG-UI events over same-origin SSE (cookie authentication, CSRF on POST)
        │
HYPRN MVP application (FastAPI)
  agent_runtime: session ↔ provider session map, journal, proposals, budgets, kill switch
  bridge binding per provider: Claude Managed Agents | OpenAI Agents API
     - registers the ToolSpec list as custom or function tools (no built-in tools, no sandbox)
     - consumes provider SSE server-side; executes tools through Registry.invoke (in-process ASGI)
     - re-emits AG-UI events (ag-ui-protocol, MIT); stores the transcript
  agent_tools registry
        │
HYPRN MVP API /api/1 → store / modeling coordinator / dispatcher → AiiDA → attested worker
```

Why this combination:

- **Criterion 1 (no duplication).** No component executes models, owns graphs or schedules work. The managed runtime only runs the conversation loop; WhatsOpt, OpenMDAO and AiiDA stay behind the HYPRN MVP API.
- **Criterion 2 (licence).** Every adopted piece is MIT or Apache-2.0: assistant-ui, AG-UI core, client and Python packages, the optional AG-UI Claude Managed Agents adapter, and the `anthropic` and `openai` SDKs. The provider runtimes themselves are paid services under provider terms, which is the chosen model, not an open-source dependency.
- **Criterion 3 (acceleration).** assistant-ui removes the hardest generic chat UI work. AG-UI gives a documented event vocabulary, including interrupts, instead of inventing one. The Anthropic side already has a working mapping to copy or depend on. What HYPRN MVP still builds is what is specific to HYPRN MVP anyway: tool renderers, proposal cards, the registry and the session binding.
- **Criterion 4 (neutrality).** Provider differences are confined to one Python binding each, behind the bridge's provider seam. The browser wire (AG-UI) and the UI library never see a provider. HYPRN MVP confirmations do not depend on either provider's approval features.

Delivery notes:

- Start with the first provider chosen for the pilot, and add the second binding behind the parity gate before general availability; writing it early tests neutrality. The Claude Managed Agents binding can start from the MIT AG-UI integration, but it should be reviewed and probably vendored. Its README warns that client-supplied thread ids act as bearer identifiers, so HYPRN MVP must bind threads to the delegating user's session.
- Pin exact versions (assistant-ui is 0.x; both runtimes are beta) and add a contract test per binding that replays recorded provider event streams.
- For the local Codex and Claude Code desktop path, ship the MCP adapter with text plus `structuredContent` results and link-based confirmations. MCP Apps UI resources could be added later for Claude and ChatGPT hosts; their rendering in the two desktop coding apps is unverified, so they must never be required.

## 6. Main risks

| Risk | Effect | Mitigation |
|---|---|---|
| Both managed runtimes are beta; event names and semantics may change. | Binding breakage. | One binding per provider, recorded-stream contract tests, pinned beta headers, upgrade reviews. |
| Neither runtime is eligible for zero data retention; OpenAI is US-only; the provider holds the transcript and session state. | Disclosure and residency exposure for study content. | Confirm retention and region before any cloud pilot; send only projections; delete provider sessions in step with HYPRN MVP retention. |
| assistant-ui is pre-1.0, and headless primitives may still conflict with the rule that screens use only design-system components. | Churn; design-system review friction. | Wrap the primitives once inside `ui/src/design` chat components; pin versions; CopilotKit or AI SDK UI as fallbacks. |
| No AG-UI adapter for the OpenAI Agents API. | Extra build effort on the OpenAI side. | A small mapping (`requires_action` → tool call, `output_text.delta` → text events); watch the AG-UI repository, where the OpenAI Agents SDK integration is in progress. |
| Provider approval features are inconsistent (Claude's do not cover custom tools; OpenAI's are undocumented for the Agents API). | Temptation to rely on provider gates. | Keep confirmations solely in HYPRN MVP. Never treat provider approvals as HYPRN MVP confirmations. |
| Vendor and licence drift in the chat ecosystem: Open WebUI and LobeHub relicensed; Tambo Cloud and Agent Builder shutting down; CopilotKit's paid tier keeps growing. | A future dependency becomes unusable. | Prefer protocol-level dependencies (AG-UI) and headless libraries that are cheap to replace; re-read the LICENSE at each upgrade. |
