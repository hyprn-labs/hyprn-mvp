# Engineering and scientific workbench platforms, and the capability map

Research date: 2026-10-12. Part of the workbench market study; the synthesis is in [recommendation.md](recommendation.md). Research input, not a decision.

Scope: (1) what WhatsOpt, OpenMDAO, AiiDA and AiiDAlab already provide that a cloud workbench must reuse or must not re-implement; (2) whether any open-source scientific or engineering workbench platform could serve as the base or a component of the HYPRN MVP workbench (home, workspaces, studies, documents, collaboration, study workbench with canvas and assistant); (3) commercial patterns worth learning from.

Method: licences were checked by reading the current LICENSE file of each GitHub repository through the GitHub API on 2026-10-12, not by trusting the SPDX badge (several show NOASSERTION while the file is plainly Apache-2.0, MIT or BSD). Release dates and approximate contributor counts come from the same API calls on 2026-10-12. Contributor counts are approximate (GitHub contributors endpoint, anonymous contributors included). Vendor capability statements in section 4 are company claims and were not independently verified. Anything not confirmed from a primary source is marked **unverified**. Canvas, real-time collaboration and chat runtimes are covered in more depth in [workspace-collaboration-canvas.md](workspace-collaboration-canvas.md) and [assistant-chat-layer.md](assistant-chat-layer.md); this report touches them only where a workbench platform bundles them.

## 1. Architecture constraints applied

These come from the architecture specification (`docs/specs/architecture-and-contracts.md`):

- Every client (UI, assistant and MCP, others) uses the HYPRN MVP API. The UI is independently implemented and controls navigation, graph presentation, inspection, source editing, optimization configuration, runs, records and assistant activity. WhatsOpt routes, ids, serializers, authentication and CLI never reach clients.
- One owner per data category: the modeling service (WhatsOpt) owns editable composition and immutable model revisions; HYPRN MVP owns studies, documents, scientific context, assessments and configurations; AiiDA owns process lifecycle and retained artifacts; OpenMDAO owns solver and optimizer state inside the worker; the UI owns only unsaved editor state. No second editable graph.
- Candidate code runs only in the currently attested restricted worker. Saving, import and static validation never import candidate code.
- No replacement solver, derivative engine, optimizer, scheduler or provenance platform.
- WhatsOpt is AGPL-3.0 (LICENSE file confirmed 2026-10-12, https://github.com/OneraHub/WhatsOpt). Its code stays inside the private modeling service and its compliance scope; it is never copied into HYPRN MVP client packages.

Two consequences matter for every candidate below. First, any platform whose core value is "users run arbitrary code in their own server" (JupyterHub, Renku sessions, marimo, AiiDAlab apps) conflicts with the restricted-worker rule unless confined to a separately isolated, opt-in sidecar. Second, any platform that owns its own workflow engine, job store or provenance graph duplicates AiiDA, and any platform that owns its own editable system graph duplicates WhatsOpt.

**What none of the backbone provides.** No component offers a multi-tenant home with workspaces and settings, workspace-level documents and evidence, HYPRN MVP's study, assumption and assessment records, immutable configurations linked to evidence, an assistant that acts through the same authorized operations, or real-time collaboration on those records. WhatsOpt has users and sharing, but scoped to its own analyses and behind a private boundary; AiiDAlab has a home page, but it is an app launcher for one Jupyter environment. The workspace, study and assistant layers are therefore HYPRN MVP's to own, and building them is not duplication. The duplication risk lies in workflow, provenance and job stores, editable graphs, solver, optimizer and DoE logic, and OpenMDAO-style viewers.

**Converging patterns**

1. **A governed project or data hub comes first, the assistant second.** VOLTA, HEEDS Connect and 3DEXPERIENCE all treat versioned process and data management with role-based sharing as the base, and the assistant sits on top. This matches HYPRN MVP's workspace → study → immutable configuration, run and evidence structure.
2. **Deterministic engines, with agents choosing and configuring.** Synera, ESTECO, Rescale and SimScale all keep the numerical workflow deterministic and let the agent pick, parameterize, validate and report. This is HYPRN MVP's rule that the assistant uses the same authorized operations, with OpenMDAO and AiiDA doing the work.
3. **Named, scoped agents or skill libraries** rather than one general chatbot: 3DS LEO, AURA and MARIE with competencies, the Rescale Agent Library, Jupyter AI personas.
4. **Assistants embedded at the point of work.** Examples are the Ansys Mesh and Validation agents, SimScale inside Onshape, and Modelon inside Impact. Each assistant is tied to the current object and can propose concrete changes for review (Theia AI change sets; Jupyter AI approval prompts).
5. **Human approval and expert control are explicit selling points** (Rescale "experts in control", Jupyter AI permissions, SimScale governance messaging).
6. **The generated report is the deliverable.** SimScale and Rescale both lead with an automatically generated validation report.
7. **Surrogate or "AI physics" workbenches are a separate area** next to the simulation workbench (PhysicsX, Rescale AI Physics, HEEDS neural-network builder, Neural Concept). For HYPRN MVP this belongs to later, separately scoped surrogate or uncertainty work, executed by OpenMDAO surrogates or OpenTURNS, not to the core workbench.

## 5. Recommendations

**R1. Build the home, workspace and study shell on the existing React (design system) plus FastAPI stack. Do not adopt a workbench platform as the base.** Every evaluated base fails at least one hard criterion or the architecture:

- notebook-centric platforms (AiiDAlab, JupyterHub and JupyterLab, marimo, Renku sessions) make "the user runs arbitrary code in their own server" the core primitive, which bypasses the attested worker and the HYPRN MVP API;
- workflow platforms (Galaxy, pyiron, Elyra, RCE, SimStack, Kadi's workflows) duplicate AiiDA;
- MDO frameworks (GEMSEO, CoSApp) duplicate OpenMDAO;
- modeler frameworks (Sirius Web, SysON) would create a second editable graph next to WhatsOpt;
- IDE shells (Theia) fight the approved screen composition and are EPL-2.0.

The shell itself (navigation, workspaces, membership, settings, documents, study pages) is ordinary web-application work. It is where HYPRN MVP's differentiation lives, and none of the backbone provides it, so building it is not duplication.

**R2. Make the backbone visible through the HYPRN MVP API instead of rebuilding it.** Concretely:

- produce OpenMDAO N2, inputs, optimizer and scaling reports and CaseViewer output in the restricted worker as retained AiiDA artifacts, and show them in a sandboxed frame in the study workbench;
- drive result tables and plots from the OpenMDAO case recording;
- derive run lineage and "what produced this value" from the AiiDA provenance graph and QueryBuilder;
- use AiiDA archives for portable run export;
- delegate model exports (OpenMDAO, GEMSEO, CMDOWS, CSV, XDSM) to WhatsOpt through the Modeling Backend Contract.

These are the highest-leverage accelerations available, because they cost integration rather than invention.

**R3. Reuse small, permissive UI components inside the custom shell:** XDSMjs (Apache-2.0) for XDSM views, React Flow (MIT) for structural and lineage canvases, Yjs (MIT) for co-editing documents owned by HYPRN MVP only, and optionally Excalidraw (MIT). Treat elkjs as EPL-2.0 (acceptable unmodified, with notices). Exclude tldraw on licence grounds. Canvas edits to model structure must become typed, revision-checked Modeling Backend Contract commands, never local graph state.

**R4. Model the assistant on the converged market and open-source pattern, without adopting an IDE runtime.** Use HYPRN MVP's tool layer (MCP server and provider bridge, `docs/agents/tooling-spec.md`) exposing the same typed operations as the UI. Keep agents scoped to tasks (modeling, configuration, evidence and report). Show proposed edits as previewable change sets (the Modeling Backend Contract preview operation already exists), with explicit human approval for commits and runs. jupyter-ai's approval model and Theia AI's change sets are the open-source references; Rescale's Agent Library, the 3DS companions and SimScale's report-first agent are the commercial ones. Provider choice (Claude or OpenAI managed agents) is orthogonal; see [assistant-chat-layer.md](assistant-chat-layer.md).

**R5. Keep AiiDA access internal.** Call AiiDA in-process from the application, or later through aiida-restapi (MIT, FastAPI, active but not released beyond v0.1.0a0) on a private network. Never expose the Flask REST API or aiida-restapi to clients. Re-evaluate aiida-restapi once it publishes a stable release.

**R6. HYPRN MVP owns tenancy.** Do not reuse WhatsOpt's users, projects, co-owner sharing or API keys for cloud workspaces. Map HYPRN MVP workspace and study membership onto the authenticated scope the modeling service enforces, as the architecture requires.

**R7. Defer, with explicit triggers:**

- an "expert notebook" sidecar (JupyterHub or marimo), only if it runs as an isolated, attested environment that talks to HYPRN MVP through scoped tokens;
- trame, only when 3D field or geometry visualization enters scope;
- SysON or SysML v2, only as an interoperability target for MBSE;
- Renku-style data connectors, as a pattern for workspace data sources;
- Persalys, as a UX reference when uncertainty work starts.
