# Contracts

The authored JSON Schema files (`schemas/model.schema.json`, `schemas/documents.schema.json`), generated execution projection (`schemas/execution.schema.json`) and the OpenAPI documents are the machine-readable wire contract:

- `hyprn-mvp.openapi.yaml`: the public HYPRN MVP API (`/api/1`), generated by `application/generate_contract.py` from the actual routes and the closed domain schemas. UI types are generated from it.
- `modeling.openapi.yaml`: the private Modeling Backend Contract (`/modeling/1`) between the application and the modeling service.

If prose here and a schema disagree on a field, the schema governs. Architecture, guarantees and versioning rules are specified in `docs/specs/architecture-and-contracts.md`; the Documents contract is in `documents.md`.

## Domain terms and wire names

Domain language is defined in `CONTEXT.md`. Several persisted wire names predate it. They stay exactly as they are: no field, schema, record or link is renamed and no data is migrated for terminology. Read each one as its domain term. In product language "package" means only a **method package** (a future concept with no wire name yet). Portable model records, execution bundles and computational record exports are never called packages.

The XDSM view has no wire name: it is a UI diagram derived from a model version and is not executable source. An XDSM-based exchange could not by itself reproduce an executable model version, which is why portable model records carry exact source.

### Analysis execution lifecycle (owner-approved, 2026-10-20)

Analysis content/version 4 adds required `estimate_plan`: null for calculations only,
or explicit output tolerances. Sampling requests 5/6 carry that plan into the generated
version. Earlier concrete formats remain unchanged. GET/POST on
`analysis-versions/{version_id}/execution` reads/launches one durable execution per version.
The launch body is empty: settings come only from the saved version. Repeated launch
returns the same execution, including after completion or failure. Existing runs are
selected once at launch; missing runs use stable commands. The existing dispatcher
advances calculations and the pinned surrogate build. Every requested output in every
group must pass validation for completion. Standalone fit/run-request endpoints refuse
format 4; old records retain their historical readers and compatibility endpoints.

### Validation terminology (owner-approved, 2026-10-19)

New sampling requests use `SampledGroup2.validation_count`; new saved sampled
analysis content is version 3 with `SampledPoint2.partition` equal to `training`
or `validation`. New estimates use format 2 and the same role names. Readers admit
predecessor formats without modifying their bytes, pins or hashes. Legacy request
formats remain accepted for compatibility. The current attested numerical protocol
retains its original `check_count`, `check` and `checks` names behind the application
adapter; renaming it requires a separately attested runtime, not a data migration.
This supersedes the terminology-only prohibition above for these successor formats.
Validation means numerical agreement with the original model, not physical validation.

## API call sequence

Typical order for an API client. Every mutation needs the session cookie, the exact `Origin` and `X-CSRF-Token`; each command carries a fresh `command_id`, and retrying the same command is idempotent.

Account display settings use the human-only self-profile boundary: `GET /profile`
returns `UserProfile1`, and `PUT /profile` accepts only `display_alias` and
`expected_revision`. This mutable preference uses revision comparison, not the
scientific command journal. After uncertain delivery, read the current profile
before retrying. Login includes the same profile. An alias is non-unique display
text (up to 128 characters, trimmed, no controls), never a login or actor identifier.
Null or blank restores the account name. New attribution and human conversation
records capture the effective display name once; reads of old records never
substitute the current viewer or a later alias.

1. **Study**: `POST /studies` creates the study. Scientific framing is edited only through `/studies/{id}/brief/draft` and saved through `/brief/versions`; there is no study-context PATCH operation.
2. **Evidence**: `POST /studies/{id}/evidence`; new versions through `/evidence-families/{id}/versions`.
3. **Model**: `POST /studies/{id}/models` with `expected_revision` = the current study `revision` (not empty, not a model token). Creation advances the study revision, so re-read the study before the next study-level write. Import (`/model-imports`) follows the same rule.
4. **Model edits**: `POST /models/{id}/preview` (optional dry run) and `/edits`, both with `expected_revision` = the draft's current `draft_revision`. Preview returns a temporary projected token; keep using the saved draft token. Then `POST /models/{id}/commits` with `expected_revision` = the `draft_revision` to freeze; the response is an immutable model version (`model_revision_id`).
   - **Rebind after a definition edit.** `revise_definition` (including quantity definitions) creates a new definition version, but every instance stays pinned to its old version. Add one `replace_local_instance_version` edit per instance: `expected_definition_version_id` = the instance's current pin, `version_ref` = the new `definition_version_id` (or the `{temp_key}` of the `revise_definition` edit in the same batch). Use `selective_rebind` with an explicit `port_map` when port identities change. Nothing rebinds automatically.
5. **Modeling approach**: `POST /approach/preview`, then `POST /approach/draft` (saves the editable draft and its revision), then `POST /approach/versions` (saves an immutable version).
6. **Configuration**: `POST /configurations/preview` returns `request_digest` (digest of the request) and `candidate_digest` (digest of the resolved configuration). `POST /configurations` takes `expected_preview_digest` = the preview's `candidate_digest`, not `request_digest`; a mismatch is `409 reference_conflict`. For a new configuration send `configuration_id: null` and `expected_revision: null`; for a new version send the `configuration_id` and its current head `configuration_revision_id` as `expected_revision`.
7. **Run**: `POST /runs` with `configuration_revision_id`; poll `GET /runs/{run_id}`. Criterion evaluations are `history.results.criteria`; `history.assessment` only identifies the evaluator.

Proposed changes, not implemented: a field pointer on the configuration-commit `reference_conflict` (today `ContractError` gives field diagnostics for schema failures only), automatic rebinding after a definition edit, and run timing and criterion-outcome summaries on a light run read.

## Boundary rules

- **Model preview** returns a temporary projected draft token, not the original `expected_revision`. The application and the modeling service check the requested original revision before projecting. Returned study and model identities and source hashes stay validated. Applying uses the original saved draft token; preview identities never become persistent identity promises.
- **Native store identifiers.** `association.store_uuid` in `ArchiveRun` and `ApproachRunContext1` follows the `NativeSource` rule: either 32 lowercase hexadecimal digits or lowercase dashed UUID text. The stored representation is kept exactly; records and hashes are never rewritten. Public resource identifiers and native process identifiers still require canonical dashed UUIDs. Native-store equality, exact associations, checksums and closure validation stay mandatory.
- **Export limits.** Computational record exports keep all limits and mandatory ancestors. `limit_exceeded` uses closed diagnostic fields to distinguish the 32 MiB expanded-byte limit (`expanded_bytes_limit`) from pending-request capacity (`pending_requests_limit`). Curated diagnostics survive asynchronous failure; arbitrary backend text and paths never do. A rejected admission allocates no request.
- **Private modeling requests** bind study, actor, resource permissions, HTTP method, full path, raw body hash and a short expiry to the separate service credential.
- **Recorded exception to "existing shapes are never edited".** Two read definitions were widened in place during early development, before any record was released: `ModelPackage` admits `ModelPackage4`, and `ExecutionVersions` admits execution bundle version `"8"`. The widened bodies are the accepted definitions. Every prior definition is now pinned individually by the contract tests, so any further in-place change fails; new shapes are added only as new versioned definitions.

### Approved additive unit exception

On 2026-10-15 the owner approved widening only the physical expression enumeration
in `UnitDeclaration1` and its matching `UnitCatalog1` discovery enumeration/count,
without introducing new record formats. The exact 20 added
spellings are `m**3`, `cm**3`, `mm**3`, `kg/m**2`, `g/m**2`, `1/m**2`,
`J/(kg*K)`, `kJ/(kg*K)`, `J`, `kJ`, `MJ`, `W`, `kW`, `MW`, `m**3/s`,
`kg/s`, `m/s**2`, `N*m`, `W/(m*K)` and `W/(m**2*K)`.

The contract guard removes only this exact suffix before checking the original
schema hash. Existing spellings and conversion factors remain unchanged. Saved
records and retained artifact schemas are not rewritten. New preparation pins the
expanded catalogue and current schema; worker source and catalogue attestation
remain mandatory. This exception does not authorize other in-place schema changes.

## Modeling contract wire notes

- `create_definition` uses `kind: "create_definition"` as the edit discriminator and `definition_kind: "explicit_component"` for the definition type, because both cannot occupy the JSON key `kind`.
- Successful `/models` and `/imports` return HTTP 201. The new model and root IDs are in the returned draft; temporary batch mappings are returned as `created_ids` by edits and preview, which also return `diagnostics`. The schemas describe these closed envelopes, capabilities, validation results and stored receipt outcomes. Receipts keep their original result, without transport envelope fields.
- Prepared file downloads use `ByteFile`, which permits bounded base64 Python or JSON bytes. `Source` remains Python-only. Static validation checks typed structure, graph references, source encoding, hashes and bounds; it does not certify Python syntax and never executes imports or discovery.
- `generator_identity.source_commit` is the literal 40-character pinned upstream source commit. `template_digest` binds the adapter's exact generator and service source plus the engine-derived unit catalog; the service image and the full patch SHA-256 are recorded separately. A changed generator or catalog changes this identity. An upstream git SHA is never relabelled as a content hash.
- **Portable model records** (wire `ModelPackageN`) contain canonical version JSON and exact decoded source-byte manifest entries. File IDs are deterministic from versioned relative paths; hashes and lengths cover the actual bytes. Files are sorted by path, ancestry is ordered oldest to newest, and source objects keep canonical base64 and all original bytes. Import recomputes the entire manifest, validates every source and version digest, and rejects collisions, incomplete ancestry, duplicate manifest entries, unsupported content and path changes. It keeps the originating service, capability and licence metadata. Nothing is extracted to caller-supplied paths.

## Units

`GET /capabilities` advertises `unit_compatibility` with the pinned OpenMDAO version (3.45.1), the exact `supported_units` list and `affine_conversion: false`. The vocabulary is: dimensionless (empty string), m, km, cm, mm, s, min, h, kg, g, N, Pa, kPa, MPa, K, degC, degF, rad, deg, m/s, km/h, J/kg, kJ/kg, MJ/kg, kg/m**3, g/cm**3, m**2, cm**2 and mm**2. Only compatible pairs with zero affine offset, as returned by the pinned OpenMDAO, are accepted. Unknown units and incompatible dimensions are rejected; offset conversions such as degC → K are rejected; identical known units are valid.

`modeling/generate_unit_catalog.py` calls the pinned engine once while the modeling service source is prepared, in a network-disabled, read-only, resource-bounded container, without loading candidate source. API validation only looks up the recorded pairs, spawns no process and never transforms supplied values. A configuration with `2000 m` for a `km` port is therefore compatible and keeps its value and unit exactly; the numerical conversion happens once, in OpenMDAO inside the worker. This is a deliberately finite vocabulary, not general OpenMDAO unit-expression support.

Each port declares physical units (one supported spelling), dimensionless or unspecified. Unspecified units may be saved, but commit, preparation and execution require resolved units for every port in the selected executable closure.

### Monetary unit successor

UnitDeclaration2 and model format 5 add the finite expressions `USD`, `kUSD`, `MUSD`,
`pax`, `USD/pax`, `USD/kg`, `USD/m**3`, `USD/h`, `USD/kW`, `USD/(kW*h)`, `USD/J`
and `USD/MJ`. UnitCatalog2 publishes their engine-verified monetary numerator,
scale and denominator with the catalogue digest and both engine source identities.
Unsupported currencies and aliases remain errors. No exchange rate, inflation or
implicit dimensionless conversion exists. All predecessor concrete definitions
and exact historical catalogue identities are retained.

ModelExplanationContent3 attaches `catalogue_expression`, `price_year`,
`economic_basis` and nonempty evidence links to exact instance/port IDs. Its saved
version pins the exact model digest. Monetary quantities need a complete declared
basis; connected quantities cannot silently mix price years or economic bases.
Monetary analysis reads that immutable explanation, never a later draft.
Preparation5, Bundle12, FrozenConfiguration10 and RunHistory9 retain Model5 with
Configuration6 and numerical result protocol3; ordinary predecessor models retain
their existing families.

## Tests

`contracts/tests` validate the schemas and fixtures; `modeling/tests` exercise the modeling contract against a running modeling service in fresh, isolated stores. They read the service URL and key file from environment variables (`HYPRN_MVP_MODEL_URL`, `HYPRN_MVP_MODEL_KEY_FILE`, and `HYPRN_MVP_MODEL_IMPORT_URL`, `HYPRN_MVP_MODEL_IMPORT_KEY_FILE` for a second service used by import tests; `HYPRN_MVP_MODEL_IMPORT_CONTAINER` names that service's test container when it is reached through the private test transport):

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m pytest contracts/tests modeling/tests -q -p no:cacheprovider
```

Never point tests at a store holding real work. Never open a live SQLite store from the host while its container writes; run queries inside the container.


## Authored schemas and the execution projection

`schemas/model.schema.json` authors model contracts and shared citation definitions.
`schemas/documents.schema.json` authors Documents-only definitions and its normative
`x-hyprn-mvp-documents-contract` registry. Names are disjoint. The Documents source also
owns its definition-order groups: each group follows a named model definition, preserving
the public contract's existing order without coupling the attested source to Documents names.
Consumers use `hyprn_mvp_app.contracts.definitions()`, `definition(name)`, `validator(name)`
and `documents_contract()`; no consumer maintains a schema copy.

`schemas/execution.schema.json` is generated from the reviewed `EXECUTION_ROOTS` and
their transitive references, in authored order. Regenerate it with
`python3 -B application/generate_execution_schema.py`; add `--check` to refuse any difference.
Never edit the generated file by hand. Root validators load only this generated schema.
Importing the contract owner opens no schema; other definitions are loaded on first use.

The execution and modeling inventories retain both model and execution schemas. Documents
belongs only to the application inventory. Changing a retained input requires the reviewed
rebuild and re-attestation. Historical prepared artifacts keep their own schema identities,
source bytes and generator digests; admission never substitutes current schema content.

## Current results and exact historical records

Prepared artifact3 pins result protocol2. Bundle10 explicitly records its input layout;
result2 and history7 omit aggregate convergence, optimization, completeness and applicability.
Execution, all output values/availability/reasons and criterion outcomes remain closed and
validated. Per-output missing values remain null and cannot satisfy a criterion.

Historical result1, preparations and bundles retain their exact schemas and bytes. Public
read views omit obsolete result fields recursively, including prior-run contexts in saved
approaches and configurations. Each changed enclosing object carries `record_view` with
`source_sha256` and `view_sha256`: canonical JSON identities, not an authenticity claim.
Existing pinned digest fields identify the unchanged source. Exact artifact downloads and
computational archives retain historical bytes. Public views cannot replace exact saved
records or their hashes. New run contexts use format2, and closures containing them use
format4; these formats do not rewrite prior contexts.

## Operational execution budget and model format discovery

Run submission accepts optional `execution_budget: {wall_seconds: integer}` from
1 through 3600; omission uses the attested 300-second default. The command digest
binds an explicit budget; changing it on replay is a payload conflict. The native
process records the effective budget as an immutable input and passes it to the
restricted launcher. The outer job allowance is that budget plus 60 seconds. This
is container-startup plus execution wall time, independent of HTTP waiting and
scientific numerical settings. The attested policy fixes default and upper bound;
per-run selection within that policy requires no re-attestation.

The additive public run-detail `execution_diagnostic` projects only bounded,
curated retained launcher metadata. It is independent of `history.results` and
criterion evaluations. Missing or invalid diagnostics remain unavailable. Retained
records are not rewritten; earlier artifacts without a budget return null for it.

`capabilities.model_formats` distinguishes create-request format 3 from current
edit/saved-model format 4. These are serialization formats, not scientific model
versions. The owner-session `create_model` and edit/preview tools supply the
appropriate format; unsupported explicit formats receive a `/schema_version`
diagnostic. Existing format semantics and the private modeling contract stay intact.

## Incremental original-model sampling

`POST /studies/{id}/exploration-samples/preview` resolves exact answer/configuration
references, explicit category tuples and budgets without numerical work or writes.
`POST /exploration-samples` retains that request and advances it through the existing
dispatcher. `GET /exploration-samples/{operation_id}` reads retained progress only;
the `/controls` subresource accepts idempotent cancel, reconcile and resume commands.
Owner-session tools expose the same public operations.

Each combination names an exact baseline and an ordered list of numerical dimensions
with bounds and units. Unvaried free assignments stay explicit in every full vector.
Category dimensions declare their allowed values; the combination list declares the
supported joint tuples, without generating an implicit Cartesian product. Current
limits are 8 tuples, 32 varied inputs per tuple, 128 retained points per operation,
3–64 training and 2–64 independent checks per tuple, and concurrency exactly 1.
No default ranges, seed, targets, budgets or category bindings are inferred.

An extension references `previous_operation_id`. Compatible coordinates and their
training/check partitions are retained; seeded SciPy Latin-hypercube batches append
only the deficit. The union of batches is not claimed to be one re-stratified LHS.
Original-result identity includes model/source, numerical settings, runtime, category
values and the complete ordered value/unit vector; targets, budget and density do
not change it. Recorded failed/unavailable results remain inspectable through their
run references and are never promoted to successful values or silently retried.

The additional-evaluation budget charges accepted scalar attempts, including failures.
Admission reserves each new point's requested execution allowance. The operation wall
budget is an elapsed admission deadline: no further point is accepted without its
remaining allowance. The existing hard per-run container limit still applies;
preparation, native-process startup and reconciliation time are reported separately
by the existing run lifecycle and are not a hard total-operation wall guarantee.
Cancellation stops future acceptance after the current bounded scalar receipt is
reconciled; it does not forcibly kill an already accepted native process. A cancelled
unresolved scalar keeps its operation slot until explicit reconciliation establishes
the outcome. Resume keeps the same deadline and budget. A new extension declares a
new additional budget.

Stable per-point command IDs recover interrupted configuration/run acceptance.
An uncertain scalar launch is resolved only through its original receipt and native
lookup; no age, retry or restart authorizes a replacement launch. An unknown numerical
design artifact remains explicitly uncertain and never starts scalar evaluations.
Generated designs are canonical data-only JSON artifacts with retained AiiDA creator
links and hashes; no estimator serialization, executable upload or new store is used.
These sample operations do not fit a surrogate or change a previously ready version.

### Declared exploration controls

`POST /studies/{id}/exploration-designs` saves an immutable `ExplorationDesign1`
receipt without numerical work. Its request declares independent category dimensions,
supported tuples, exact configuration/model version pins, one initial axis and every
free input's saved-unit range, optional step, optional explicit covary group and
optional compatible common-selection key. Connected ports cannot be controls.
Both bounds may be null; this is an explicit missing range, never a physical default.
The read endpoint keeps the exact design; answer-filtered design and sample listings
return at most 20 records with a cursor. Every endpoint uses ordinary study access.

`ExplorationSampleRequest2` / `ExplorationSampleOperation2` add complete declared
dimensions, steps and covary bindings while keeping version 1 shapes unchanged.
The application maps bounded numerical design coordinates to the declared grid in
saved units and expands covary groups before scalar submission. Every transformed
full vector and partition is retained in the sample manifest; its design digest
binds both the numerical design and transformed points. Repeated vectors after
mapping fail before any scalar launch. Training and independent checks never share
a mapped vector. Insufficient finite grids and missing ranges are refused before
design generation. No unit conversion or numerical model runs in the browser.

## Prepared linked-input slices

Exploration request format 2 adds explicit `varying_targets` to the existing
seeded one-dimensional design/fit operation. It includes the selected `axis` and
only free occurrences with equal baseline values and identical model units.
Every listed assignment follows the selected coordinate; every other assignment
must match the frozen baseline. Equal names never establish this relationship.
The restricted numerical operation and exact training/check partition are unchanged.

Prediction format 2 includes `sample_outputs`, ordered by `samples` then request
`tolerances`, projected from the checked retained original results. Null remains
unavailable. The existing sample run IDs and result digests identify each original;
this compact projection avoids hydrating a full native history per plotted marker.
Format 1 requests and saved responses remain unchanged. Public preparation reads
admit both formats. Single-input interaction returns other inputs to the saved
baseline explicitly; combined-input interaction still requires complete-vector
coverage and never combines independent slice estimates.

## Structured authored evidence content

`schemas/evidence-content.schema.json` defines a versioned **note-body format**,
not a change to the frozen EvidenceCreate/Record envelopes. Content starting with
`HYPRN evidence/1` followed by one newline contains a JSON object with `excerpt`,
`source_reference`, `location`, and `explanation`. All four are nonempty strings;
the existing 4096-character total content limit still applies. The API rejects
malformed marked content before storage. Duplicate JSON keys are rejected.
Unmarked historical text remains uninterpreted prose. This explicit encoding keeps
all existing snapshots, pins, exports and execution schemas unchanged; no second
store or mutable source lookup is introduced. The source transcription is supplied
by the author, never labelled authenticated by the application. This is separate
from the future resolver-backed DocumentCitation contract.

The owner study helper accepts the object directly in `body.content`, serializes
it for the public API and advertises the content schema. Agent readers return
separate untrusted fields. Reading a note never follows its source URLs.

## Case removal — authorized demo contract transition (2026-10-17)

The product owner removed Case as a platform primitive. Approach content, selections,
usage and run listings no longer expose case fields. Scientific answers directly
cite configurations, runs and evidence and have one head per approach version.
This is an explicitly authorized breaking change to the affected concrete schemas,
not a general exemption from schema freezes. Incompatible development records must
be exported and replaced, never silently rewritten under their old identities.
See ADR 0006. Execution schemas and attestation must be regenerated before execution.
